## Must-fix

1. On a contest the caller owns, every unclaimed roster row with a null `user_id` is renamed to `Deleted player`, including a guest name the owner typed. `callerRosterIds` does that at `scoresnap/supabase/functions/delete-account/purge.ts:123`. The comment at `:101-102` says the guest is included because the row looks like the host slot. `sync_round_bundle` inserts every player with no `user_id` (`scoresnap/supabase/migrations/20261028100000_tournament_rounds_live.sql:325-327`). `HOST_SLOT` only stops the owner from taking a membership (`scoresnap/supabase/migrations/20261027120000_sync_foundation.sql:121`). A guest nobody claimed has the same columns as the host. On the surviving `roster` contest, Sam's roster name, snapshot `displayName`, and chat `display_name` all become `Deleted player` while Sam's scores stay (`account-deletion.scenario.ts:314`, `:375`, `:379`). Blair keeps that contest. Sam is not the deleted account. The same shape on a contest the caller does not own is left alone (`Pat` at `:312` and `:368`), so ownership of the contest, not whose name the row is, decides. The scenario asserts the wrong result, so this suite cannot catch it.

   Narrowest correct rule: rename a roster row only when `contest_players.user_id` is the caller, or when `contest_memberships.user_id` is the caller and `player_id` is that row (`purge.ts:116-122` already does those two). Leave every other null `user_id` row, including a guest the owner typed. The host slot from round 1 is still real, and it is stored the same way. Identify it by writing the owner's `user_id` onto the owner's roster row when the round is synced. The new-contest screen already starts player 1 as the signed-in user (`scoresnap/app/contest/new.tsx:75-87`). `profiles.display_name` cannot do that job: signup never writes it, and `purgeAccount` does not read it. A contest with no other account is still deleted entirely, guests included, because `owner_id` is `NOT NULL`. That path is `deleteContest`, not a rename.

2. The contest delete can commit the score-log removal and then fail, leaving the contest in place. `score_events.round_id` references `contest_rounds` with `ON DELETE RESTRICT` (`20261028100000_tournament_rounds_live.sql:123-126`). `deleteContest` deletes `score_events` and then `contests` as two PostgREST calls (`scoresnap/supabase/functions/delete-account/supabase-repo.ts:81` and `:83`). Each call is its own transaction. PostgREST `db-max-rows` does not limit a DELETE that has no `limit`, so the first call removes every event for that contest and commits. If the second call errors or the function stops between them, the contest, its rounds, the guest roster, and the published snapshot remain, and the append-only score log is already gone. The handler then returns 500 and does not delete the auth user (`scoresnap/supabase/functions/delete-account/handler.ts:35-39`). The memory repository applies both removals inside one function, and `account-deletion.scenario.ts:649-651` only checks that the two calls are ordered `score_events` then `contests`. Neither fails the second call.

   The purge is not transactional. `purgeAccount` (`purge.ts:164`) awaits each repository method on its own. A throw stops later steps, including `auth.admin.deleteUser`, and the earlier writes stay. `round_scorer_scopes` for the caller are deleted (`supabase-repo.ts:265-267`) and `group_submissions.submitted_by` is moved to the current owner after ownership transfer (`:269-284`). Those two are the right changes for the M3 foreign keys (`user_id` and `submitted_by` reference `auth.users` with no `ON DELETE` at `20261028100000_tournament_rounds_live.sql:65` and `:78`), and the scenario checks them (`account-deletion.scenario.ts:418-423`). They commit independently of the contest delete. The narrow fix for the partial contest is one database statement that deletes that contest's `score_events` and then the contest, so both roll back together.
