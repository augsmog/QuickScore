# GS-14 slices 1–2: live scoreboard and round chat

Organizer signs in with real Supabase auth and taps **Share live scoreboard**. The owner RPC creates a server contest mapping for the local ID, publishes an allowlisted snapshot, and returns a fresh 64-character capability (two cryptographically random UUIDs). Only its SHA-256 hash is stored. Each copy creates a new link; **Revoke live links** revokes every link for that round. Tokens stay in UI memory, not persisted in the contest store.

The public `/r/<token>` web page needs no login or onboarding. It shows display names, hole scores, totals, relative-to-par scores and provisional game results (settlement engine at a one-unit stake, no private betting amounts). No course/location, contact details, IDs, handicaps or raw contest data are published. Names are organizer-selected display names; organizers should avoid putting contact information in them.

The public page uses **5-second polling** for scores and chat, not Realtime subscriptions (slice 1 originally used 10 seconds). Every fetch verifies token, revocation and expiry on the server. On errors the viewer clears the displayed snapshot; network recovery retries automatically. Revocation becomes visible on the next poll. Score changes publish serially, including imports, edits, auxiliary data and completion, only for enabled shares with real auth. Offline builds never publish. The open organizer screen retries every 10 seconds after sync failure. Keep that device online with the round open; background/device-independent sync is deferred.

Completion is the first server-observed `completed` snapshot. Links expire seven days after that timestamp, which is immutable even if the local status is changed back. Active-round links have `infinity` expiry until completion is published. An offline completion cannot reach the server until reconnect; the host can revoke immediately once online. No tokens or snapshots are logged by this feature; Sentry is disabled on public web share pages. Configure the web host to redact `/r/*` request paths from access logs, send `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, and `X-Robots-Tag: noindex, nofollow`. Never cache token RPC responses at a proxy. The page also sets referrer and robots metadata.

Guest cross-device scoring is slice 3. Private Realtime notifications, rotation UI, background retries, conflict/version handling and independent SQL security integration verification are deferred. No paid services are required.

## Slice 2: round chat

Anyone with a valid link can read chat and post after choosing a 1–30 character display name; bodies are 1–500 characters after trimming. No account or paid service is required. The name and a cryptographically random 256-bit anonymous session ID are stored locally with AsyncStorage, separately from Supabase auth. No share token is persisted. Storage must work to post; failures show a retryable error. The server stores only SHA-256 of the session, never the raw session. Display names are self-selected, not verified identities; avoid contact details.

`004_live_chat.sql` adds `round_messages` with deny-by-default RLS and no direct table permissions for PUBLIC, anon or authenticated. All five RPCs use SECURITY DEFINER with a fixed `pg_catalog` search path and fully qualified application tables. The internal `chat_contest` helper is not callable by app roles. Public `post_message` and `list_messages` validate the token, expiry and revocation on every call. Posting locks the published round (the same lock used by revoke/publish), rechecks validity after waiting, and enforces **5 messages / 30 seconds per session per round** plus **60 / minute per round**. Removed messages still count; limits span all links for that round. Clearing local storage can evade the session limit; the round cap remains. This is basic throttling, not identity-based abuse protection.

Public messages expose **display_name, body, created_at only**, with no IDs, session hashes or contest identifiers. `list_messages(token, since)` returns up to the latest 200 visible messages in chronological order. The client always sends a null `since` and replaces the visible window every 5 seconds so removals disappear; it never appends a stale incremental list. Both score and chat polling prevent overlapping requests and discard results after unmount. Failed reads clear displayed data and disable posting until recovery. Rate-limit responses preserve the draft and pause sending for 30 seconds (a busy round may require another wait). Names and bodies render through React Native `Text`, as literal text, including HTML-like input. Profanity filtering is out of scope.

While sharing is enabled, `LiveShare` shows host moderation, polling every 5 seconds. `list_host_messages(local_id)` supplies message IDs only to the real authenticated owner, checking both published-round and contest ownership. `remove_message(message_id)` checks the same ownership and soft-removes the message; other owners and anonymous users cannot remove it. **Revoke live links** blocks both scores and chat, including posts; viewers clear the composer on their next poll. Round completion and seven-day expiry follow slice 1's immutable server-observed completion timestamp.

## Apply manually (Tater; not performed by Codex)

1. Back up the target Supabase database and test these steps on a disposable development project first. Review `002_contest_sharing_draft.sql`: it is an unapplied prerequisite, not an instruction to enable guest sync.
2. In Supabase Dashboard → SQL Editor, run `select to_regclass('public.contests'), to_regclass('public.contest_guests');`. If both are absent, paste and execute **only** `supabase/migrations/002_contest_sharing_draft.sql`. If either exists, compare its schema against 002 before proceeding; do not recreate existing tables or blindly run all migrations.
3. Paste the full `supabase/migrations/003_live_share.sql` into SQL Editor and execute once. It is transactional. Record successful application in your deployment migration ledger; do not rerun it.
4. Verify RLS is enabled and neither `anon` nor `authenticated` has direct table access to `published_rounds` or `share_links`. Verify anonymous callers can execute only `get_shared_round`, and all three mutation RPCs reject missing auth or a different owner's local mapping. Confirm no broad policies inherited from a different schema expose these tables or `contests`.
5. Review and manually apply **004_live_chat.sql** once after 003; record it in the migration ledger. Verify direct round_messages reads/writes are denied for anon/authenticated, private helper execution is denied, and only real owners can list moderation IDs/remove messages. Exercise token expiry/revocation on both chat RPCs, removed-message visibility, concurrent posts at both rate boundaries, and cross-owner moderation denial on the disposable project. These database security/concurrency checks remain required; mocked tests do not execute SQL.
6. Configure the app's existing `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY`, with `EXPO_PUBLIC_OFFLINE_MODE=false`. Never put a service-role key in the app. For native organizers set `EXPO_PUBLIC_WEB_URL` to your HTTPS web deployment origin.
7. Export/deploy Expo web with an SPA rewrite for `/r/*` and the headers/log redaction above. Sign in as an organizer, create a link, and open it in an isolated anonymous browser. Change a score and verify it updates within 5 seconds. Test reconnect, revoke, completion/expiry, guessed tokens, cross-owner RPC calls and denied direct table reads/writes before going live.
