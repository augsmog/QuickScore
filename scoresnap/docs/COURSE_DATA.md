# Course data

The app uses its existing Supabase client and anon/user JWT to call the `course-data` Edge Function. JWT verification stays enabled at the gateway. The provider key (`GOLFCORE_API_KEY`) and service-role database key stay server-side. No direct provider calls occur in the app. Search is enabled only by `EXPO_PUBLIC_FEATURE_COURSE_SEARCH=true`.

The function allows GET search (`q`, or `near=lat,lng&radius=miles`), detail (`slug`), service-role count (`count=1`), and service-role usage (`usage=1`). Query length is at least two characters, radius at most 50 miles, and limit at most 50. No arbitrary paths, offsets, bulk exports, or general proxy are exposed. Search cache keys normalize case and whitespace. Search results persist for seven days, detail records for 90 days, and measured counts for 24 hours. Stale records remain available when upstream fails or the guard blocks refresh. Tables have RLS enabled and no client policies; only the function's service role accesses them.

GolfCore data stays tagged `source=golfcore` in a read-through catalog. Do not redistribute it, resell it, merge it into an owned database, or use it to build a competing database. Display “Course data: GolfCore” and link to the supplied course URL. The tee picker provides that credit. Preserve tee gender categories, ratings, stroke indexes, and missing fields. An explicit empty/partial tee card never borrows layout yardages. Only an absent tee card uses layout par/stroke indexes, with yardages left blank. Incomplete cards open manual entry for a complete 9/18-hole card before entering the scoring engine.

## Budget and ledger

Hard ceilings are 500 calls per UTC month and 9 per rolling minute; environment settings can only lower them. Each upstream attempt, including each retry, first obtains an atomic `reserve_golfcore_call` ledger reservation under a database advisory lock. A refused reservation returns immediately to cache/manual entry. There is no isolate work queue. Failed or interrupted calls conservatively consume their reserved row. Cache hits add no rows.

Per-minute 429 responses honor numeric Retry-After seconds, capped at eight seconds; absent or invalid values use two then four seconds. At most two retries occur, each with a new reservation and ledger row. After failure, stale cache carries `rate_limited:true`, or the function returns 503 `{error:"rate_limited",fallback:"manual"}`. Monthly quota signals in error bodies/headers, including a 429 with X-RateLimit-Remaining zero, never retry. They set the row's `quota_tripped` flag, which blocks reservations for the rest of that UTC month. Sleep and fetch are injectable for offline tests.

Migration 007 adds `quota_tripped`, the RLS-protected `golfcore_usage_drift` table, `reconcile_golfcore_usage`, and service-role-only `golfcore_usage_summary_v2`. It replaces the existing course-data reservation function additively; migration 006 and its v1 summary are unchanged. Each response stores the rate headers. Reconciliation compares limit minus remaining against the database month row count; a difference greater than 2% logs a drift observation. The v2 summary reports the greater of ledger rows and latest header usage as `calls_effective`, with `ledger_rows`, `as_of`, `quota_errors`, `quota_tripped`, and trailing `calls_7d` across UTC month boundaries. Projection is effective calls plus `(calls_7d / 7) * fractional UTC days remaining`. The usage endpoint returns this view without another counter or provider call.

At the monthly guard, stale search data returns `quota_exhausted:true`; the minute guard returns `rate_limited:true`. With no cached data, the function returns the corresponding 503 error and `fallback:manual`. Detail can also return stale cache. Upstream/database errors return cached data when available or a generic 503/manual response with no secrets or stack traces. The app shows “Course search is resting, enter holes manually” for quota exhaustion.

## Usage alert operation

The box checker (installed at `/workspace/aos-state/snapscore/golfcore_usage_check.py`, outside this repo; run on Tater's routine cadence) reads only `golfcore_usage_summary_v2` through the Supabase Management API SQL endpoint using `SUPABASE_ACCESS_TOKEN` from the environment. It writes `golfcore-usage.json` with `as_of`, `ledger_rows`, the unchanged summary, and level. No API token or key is printed. It does not count traffic. It is not part of the app commit. At low usage it writes no note.

Thresholds use unrounded values: `t70` at 70% effective use or a projection above 500, `t90` at 90%, and `t429` for quota errors or a tripped quota. One monthly note under `projects/golf-score-app` holds one open structured payment owner-blocker. IDs end in `-70`, `-90`, or `-429`; higher cards supersede lower cards, with durable fired/superseded history in the body. First-fire time stays fixed, verification time updates, and each threshold fires at most once monthly. UTC month rollover, or a decided note whose `chosen` is an affirmative Keep/Yes/Upgrade, clears the card; a declined or ambiguous decision keeps it open. Notes include ledger evidence and a seven-day observation table, validate with live `aos_lib`, and are written only when changed through merge_gate checkout/apply as actor tater. No board code changes.

The ask is “Upgrade GolfCore to Starter ($10/mo)?” for the golf scoring app: never automatic; Starter needs your yes. Free tier only, $0 spent. `--grep-key PATH...` requires only `GOLFCORE_KEY_PREFIX` and `GOLFCORE_KEY_LEN`, scans artifacts, and prints counts only; any prefix hit fails closed.
